### 1. **Quais casos estão diretamente apoiados pelo requisito?**

- **CT01**:  
  → Sim, está diretamente apoiado. O requisito diz: *“Um usuário deve conseguir fazer login informando e-mail e senha válidos”*.  
  → CT01 testa exatamente essa condição (e-mail e senha válidos), portanto é alinhado ao requisito.

- **CT04**:  
  → Parcialmente apoiado. O resultado "redirecionar para o dashboard" é uma consequência lógica do login bem-sucedido, mas não está diretamente no requisito original. O requisito fala apenas sobre *conseguir fazer login*, não sobre onde o usuário será redirecionado após o login.

✅ **Conclusão**:  
Apenas **CT01** é diretamente apoiado pelo requisito. CT04 é uma extensão lógica, mas não está explicitamente no enunciado.

---

### 2. **Quais casos introduzem regras que não estão especificadas?**

- **CT02**:  
  → Introduz uma regra não especificada: *senha deve ter pelo menos 8 caracteres*.  
  → O requisito fala apenas sobre "senha válida", sem definir critérios de validade.  
  → Essa exigência é um **detalhe técnico adicional** que não está no requisito original.

- **CT03**:  
  → Introduz uma regra de segurança não especificada: *bloqueio após 3 tentativas inválidas*.  
  → O requisito não menciona limites de tentativas, bloqueios ou mecanismos de proteção.  
  → Essa é uma **regra adicional**, não presente no requisito.

❌ **Conclusão**:  
**CT02 e CT03 introduzem regras que não estão especificadas** pelo requisito original.

---

### 3. **Quais resultados esperados são suposições?**

- **CT04 – Resultado: "redirecionar para o dashboard"**  
  → O resultado assume um comportamento de navegação após login (redirecionamento).  
  → O requisito não menciona nada sobre a tela ou o fluxo pós-login.  
  → Essa suposição é **incompatível com o foco do requisito**, que se limita ao *login bem-sucedido*.

- **CT02 – Resultado: "mostrar mensagem 'Senha deve ter no mínimo 8 caracteres'"**  
  → Supõe que a aplicação valida a senha por tamanho e exibe uma mensagem específica.  
  → O requisito não menciona validações de senha nem mensagens de erro.

✅ **Conclusão**:  
O resultado esperado em **CT04** (redirecionamento) e o resultado em **CT02** (mensagem de erro específica) são **suposições**, pois não estão no requisito original.

---

### 4. **Quais dúvidas deveriam ser encaminhadas ao PO?**

As seguintes dúvidas devem ser levantadas com o Product Owner:

- **CT02**:  
  → O que define uma "senha válida"? Apenas o tamanho (8 caracteres)? Ou há outras regras (como caracteres especiais, maiúsculas, etc.)?  
  → Deve-se saber se a validação é feita pelo sistema ou se depende de políticas externas.

- **CT03**:  
  → O que significa "bloquear a conta"? Por quanto tempo? Se o usuário pode recuperar acesso após algum tempo?  
  → Qual é o critério para considerar uma tentativa inválida (e-mail errado, senha errada)?  
  → O bloqueio é aplicado na tela de login ou no backend?

- **CT04**:  
  → Após login bem-sucedido, qual a página de destino? "Dashboard" é um termo técnico — o que significa exatamente?  
  → Há algum fluxo de autorização (ex: revalidação de sessão) ou dependência de outro sistema?

✅ **Conclusão**:  
As dúvidas principais devem ser encaminhadas ao PO para clareza dos seguintes pontos:
- Definição de "senha válida"
- Critérios para tentativas inválidas e bloqueio
- Comportamento pós-login (redirecionamento)
- Significado do termo "dashboard"
